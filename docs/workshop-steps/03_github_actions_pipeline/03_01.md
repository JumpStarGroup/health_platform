# Task 01 - Run the GitHub Actions workflow to deploy to AKS

## Introduction

Now that you understand the shared AKS deployment model from Exercise 02, you will trigger the existing GitHub Actions workflow to build container images, push them to **GHCR**, and deploy your Health Platform app to the shared AKS cluster in an isolated **namespace derived from your branch name**.

## Description

In this task, you will create a new branch, push changes to trigger the workflow, and observe the automated deployment process that:
- Builds Docker images for backend and frontend
- Pushes images to GitHub Container Registry (GHCR)
- Computes a namespace from your branch name
- Deploys to the shared AKS cluster with namespace-level isolation

## Success Criteria

- You have created a feature branch and pushed a commit
- The GitHub Actions workflow completed successfully
- Container images appear in GHCR
- Your namespace exists in the shared AKS cluster
- The frontend is accessible via LoadBalancer public IP

## Key Tasks

### 01: Create a feature branch

Create a new branch to trigger the deployment workflow.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Open the Terminal in Visual Studio Code

2. Create and switch to a new feature branch:
   ```bash
   git checkout -b feature/my-deployment
   ```

3. Make a small change to trigger the workflow (e.g., update README):
   ```bash
   echo "## Workshop Deployment" >> README.md
   git add README.md
   git commit -m "Trigger workshop deployment"
   ```

4. Push the branch to GitHub:
   ```bash
   git push -u origin feature/my-deployment
   ```

> **NOTE**: The branch name will be normalized to create your namespace (e.g., `feature-my-deployment-abc123`)

</details>

### 02: Monitor the workflow execution

Watch the GitHub Actions workflow build and deploy your application.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Navigate to your GitHub repository

2. Go to **Actions** tab

3. You should see a workflow run for your branch (e.g., "Build and Deploy to AKS")

4. Click on the workflow run to see detailed logs

5. Observe these key steps:
   - **Build backend image** - Builds the Flask backend container
   - **Build frontend image** - Builds the React frontend container
   - **Push to GHCR** - Pushes both images to GitHub Container Registry
   - **Compute namespace from branch** - Normalizes your branch name to a valid namespace
   - **Create imagePullSecret** - Creates/updates the GHCR pull secret in your namespace
   - **Apply Kubernetes manifests** - Deploys backend, frontend, and services to AKS

6. Wait for the workflow to complete (typically 5-10 minutes)

![Workflow execution in progress](../../media/0301_workflow_progress.png)

</details>

### 03: Verify images in GHCR

Confirm your container images were pushed to GitHub Container Registry.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. From your GitHub repository, go to the repository home page

2. On the right sidebar, look for **Packages** section

3. You should see two packages:
   - `health-platform-backend`
   - `health-platform-frontend`

4. Click on each package to see the image tags:
   - Tags include your branch name and commit SHA
   - Example: `feature-my-deployment-abc123` and `sha-1234567`

5. Verify the image size and push timestamp match your workflow run

> **NOTE**: These images are public (or organization-visible) and can be pulled by anyone with the GHCR token

</details>

### 04: Verify namespace creation in AKS

Confirm your namespace was created in the shared AKS cluster.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

> **PREREQUISITE**: You must have `kubectl` configured to access the shared cluster. If the workshop admin provided a kubeconfig, load it first:
> ```bash
> export KUBECONFIG=path/to/workshop-kubeconfig.yaml
> # Or on Windows:
> set KUBECONFIG=path\to\workshop-kubeconfig.yaml
> ```

1. List all namespaces in the cluster:
   ```bash
   kubectl get namespaces
   ```

2. Find your namespace (derived from your branch name):
   ```
   NAME                          STATUS   AGE
   feature-my-deployment-abc123  Active   2m
   ```

3. View resources in your namespace:
   ```bash
   kubectl get all -n feature-my-deployment-abc123
   ```

4. You should see:
   - 2 Deployments (backend, frontend)
   - 2 Pods (or more if replicas > 1)
   - 2 Services (backend ClusterIP, frontend LoadBalancer)
   - 1 ResourceQuota
   - 1 LimitRange

Example output:
```
NAME                                    READY   STATUS    RESTARTS   AGE
pod/health-backend-xxx                  1/1     Running   0          2m
pod/health-frontend-yyy                 1/1     Running   0          2m

NAME                       TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)
service/health-backend     ClusterIP      10.0.123.45     <none>          5000/TCP
service/health-frontend    LoadBalancer   10.0.123.46     20.30.40.50     80:30123/TCP

NAME                              READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/health-backend    1/1     1            1           2m
deployment.apps/health-frontend   1/1     1            1           2m
```

</details>

### 05: Access the application via LoadBalancer

Find the LoadBalancer public IP and access your deployed frontend.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Get the LoadBalancer external IP for your frontend service:
   ```bash
   kubectl get service health-frontend -n feature-my-deployment-abc123
   ```

2. Look for the `EXTERNAL-IP` column:
   ```
   NAME              TYPE           EXTERNAL-IP     PORT(S)
   health-frontend   LoadBalancer   20.30.40.50     80:30123/TCP
   ```

3. Open a browser and navigate to the external IP:
   ```
   http://20.30.40.50
   ```

4. You should see the Health Platform login page

5. Test the application:
   - Register a new user account
   - Log in
   - Add a family member
   - Record a health measurement (blood pressure, heart rate)

> **NOTE**: It may take 1-2 minutes for the LoadBalancer IP to be allocated after deployment completes

> **TROUBLESHOOTING**: If you see "This site can't be reached", wait a minute and refresh. If the problem persists, check pod status with `kubectl get pods -n <your-namespace>`

</details>

### 06: Review deployment details

Inspect the deployed resources to understand the AKS deployment structure.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Describe the frontend service to see LoadBalancer details:
   ```bash
   kubectl describe service health-frontend -n feature-my-deployment-abc123
   ```

2. Check the ResourceQuota applied to your namespace:
   ```bash
   kubectl get resourcequota -n feature-my-deployment-abc123 -o yaml
   ```
   
   You should see limits like:
   - CPU requests/limits
   - Memory requests/limits
   - Max number of LoadBalancers (typically 1)

3. View the imagePullSecret created by the workflow:
   ```bash
   kubectl get secret ghcr-secret -n feature-my-deployment-abc123
   ```

4. Check pod logs to verify the application is running correctly:
   ```bash
   # Backend logs
   kubectl logs -l app=health-backend -n feature-my-deployment-abc123

   # Frontend logs
   kubectl logs -l app=health-frontend -n feature-my-deployment-abc123
   ```

</details>

## Summary

You've completed this task. The GitHub Actions workflow successfully:
- Built Docker images for your Health Platform backend and frontend
- Pushed images to GHCR with proper tags
- Created an isolated namespace in the shared AKS cluster
- Deployed your application with LoadBalancer access
- Applied namespace-level guardrails (ResourceQuota, LimitRange)

Your application is now live and accessible via the LoadBalancer public IP!
