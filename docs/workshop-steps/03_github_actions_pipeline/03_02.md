# Task 02 - Troubleshoot deployment issues

## Introduction

Even with successful workflow runs, your AKS deployment may encounter runtime issues. This task covers common troubleshooting scenarios for the shared cluster deployment model.

## Description

In this task, you will learn systematic approaches to diagnose and resolve issues with your AKS deployment, including workflow failures, pod crashes, LoadBalancer problems, and image pull errors.

## Success Criteria

- You can identify and interpret workflow failure messages
- You can use `kubectl` to diagnose pod and service issues
- You can resolve common image pull and networking problems
- You understand how to check namespace resource limits

## Key Tasks

### 01: Workflow failures

Diagnose and fix GitHub Actions workflow failures.

<details markdown="block">
<summary><strong>Expand this section for common workflow issues</strong></summary>

#### Symptom: Workflow fails at "Build backend/frontend image"

**Common causes:**
- Docker build context errors (missing files, incorrect Dockerfile path)
- Syntax errors in Dockerfile
- Build timeout

**Troubleshooting:**
1. Review the workflow logs for the specific build step
2. Look for error messages like "COPY failed" or "RUN command failed"
3. Test the Docker build locally:
   ```bash
   cd c:\source\workshop\health_platform
   docker build -t test-backend -f Dockerfile.backend .
   docker build -t test-frontend -f Dockerfile.frontend .
   ```

#### Symptom: Workflow fails at "Push to GHCR"

**Common causes:**
- Missing or expired GITHUB_TOKEN permissions
- Network connectivity issues

**Troubleshooting:**
1. Verify the workflow uses `GITHUB_TOKEN` (automatically provided)
2. Check repository settings → Actions → General → Workflow permissions
3. Ensure "Read and write permissions" is enabled

#### Symptom: Workflow fails at "Apply Kubernetes manifests"

**Common causes:**
- kubectl authentication failure
- Namespace quota exceeded
- Invalid Kubernetes manifest syntax

**Troubleshooting:**
1. Check if the workflow has valid kubeconfig credentials
2. Verify the namespace exists and has capacity
3. Review the template substitution in the logs (check for missing environment variables)

</details>

### 02: Pod startup failures

Resolve issues where pods fail to start or crash immediately.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Check pod status in your namespace:
   ```bash
   kubectl get pods -n <your-namespace>
   ```

2. Look for pods with status `CrashLoopBackOff`, `Error`, or `ImagePullBackOff`

3. Describe the problematic pod for detailed events:
   ```bash
   kubectl describe pod <pod-name> -n <your-namespace>
   ```

4. Check pod logs:
   ```bash
   kubectl logs <pod-name> -n <your-namespace>
   # Or for previous crash:
   kubectl logs <pod-name> -n <your-namespace> --previous
   ```

**Common issues and fixes:**

| Status | Cause | Solution |
|--------|-------|----------|
| `ImagePullBackOff` | Can't pull image from GHCR | Check imagePullSecret exists: `kubectl get secret ghcr-secret -n <namespace>` |
| `CrashLoopBackOff` | Application crashes on startup | Check logs for Python/Node.js errors; verify environment variables |
| `Pending` | Not enough resources | Check ResourceQuota: `kubectl describe resourcequota -n <namespace>` |
| `Error` | Application exit code non-zero | Review logs for stack traces or missing dependencies |

</details>

### 03: ImagePullBackOff troubleshooting

Fix image pull authentication issues specific to GHCR.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Verify the imagePullSecret exists:
   ```bash
   kubectl get secret ghcr-secret -n <your-namespace>
   ```

2. If missing, check if the workflow step "Create imagePullSecrets" ran successfully

3. Verify the secret contains valid credentials:
   ```bash
   kubectl get secret ghcr-secret -n <your-namespace> -o yaml
   ```

4. Check if the image name/tag is correct in the Deployment:
   ```bash
   kubectl get deployment health-backend -n <your-namespace> -o yaml | grep image:
   ```

5. Test if you can pull the image manually (from a machine with docker):
   ```bash
   echo $GHCR_READ_TOKEN | docker login ghcr.io -u $GHCR_USERNAME --password-stdin
   docker pull ghcr.io/<owner>/health-platform-backend:<tag>
   ```

**Common fixes:**
- Re-run the workflow to recreate the imagePullSecret
- Verify `GHCR_READ_TOKEN` is valid and has `read:packages` scope
- Check if the image tag exists in GHCR (go to repository → Packages)

</details>

### 04: LoadBalancer issues

Resolve problems accessing the frontend via LoadBalancer.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Check LoadBalancer service status:
   ```bash
   kubectl get service health-frontend -n <your-namespace>
   ```

2. If EXTERNAL-IP shows `<pending>`:
   - Wait 2-3 minutes (Azure Load Balancer provisioning takes time)
   - Check namespace ResourceQuota for LoadBalancer limits:
     ```bash
     kubectl describe resourcequota -n <your-namespace>
     ```
   - If quota exceeded, delete old LoadBalancers from other namespaces

3. If EXTERNAL-IP is assigned but connection times out:
   - Check pod status: `kubectl get pods -n <your-namespace>`
   - Verify pods are `Running` and `READY 1/1`
   - Check frontend pod logs for errors:
     ```bash
     kubectl logs -l app=health-frontend -n <your-namespace>
     ```

4. Test connectivity from inside the cluster:
   ```bash
   kubectl run -it --rm debug --image=busybox --restart=Never -n <your-namespace> -- /bin/sh
   # Inside the pod:
   wget -O- http://health-frontend
   ```

5. Verify service selector matches pod labels:
   ```bash
   kubectl describe service health-frontend -n <your-namespace>
   # Check "Endpoints" - should list pod IPs
   ```

</details>

### 05: Backend connectivity issues

Troubleshoot when frontend can't reach backend.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Check backend service exists and has endpoints:
   ```bash
   kubectl get service health-backend -n <your-namespace>
   kubectl get endpoints health-backend -n <your-namespace>
   ```

2. Verify backend pods are running:
   ```bash
   kubectl get pods -l app=health-backend -n <your-namespace>
   ```

3. Test backend connectivity from frontend pod:
   ```bash
   kubectl exec -it <frontend-pod-name> -n <your-namespace> -- curl http://health-backend:5000/api/v1/health
   ```

4. Check frontend environment variables for backend URL:
   ```bash
   kubectl exec <frontend-pod-name> -n <your-namespace> -- env | grep BACKEND
   ```

5. Review backend logs for request errors:
   ```bash
   kubectl logs -l app=health-backend -n <your-namespace> --tail=100
   ```

</details>

### 06: Resource quota exceeded

Handle namespace resource limit errors.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Check current resource usage:
   ```bash
   kubectl describe resourcequota -n <your-namespace>
   ```

2. Compare "Used" vs "Hard" limits for:
   - CPU requests/limits
   - Memory requests/limits
   - Number of LoadBalancers
   - Number of Pods

3. If quota is exceeded:
   - Reduce replica counts in your Deployment
   - Lower resource requests in pod specs
   - Delete unused resources (old Deployments, Services)

4. View pod resource requests:
   ```bash
   kubectl describe pod <pod-name> -n <your-namespace> | grep -A5 "Requests:"
   ```

5. Contact workshop admin if you need quota increase (usually not needed for this workshop)

</details>
