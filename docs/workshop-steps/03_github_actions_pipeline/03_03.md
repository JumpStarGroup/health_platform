# Task 03 - Use Copilot and AI to troubleshoot runtime issues

## Introduction

GitHub Copilot and Copilot Chat can accelerate troubleshooting by analyzing logs, suggesting fixes, and generating diagnostic commands. This task demonstrates AI-assisted debugging for AKS deployments.

## Description

Learn how to leverage GitHub Copilot to diagnose pod crashes, network issues, and configuration errors in your Kubernetes environment.

## Success Criteria

- You can use Copilot Chat to interpret kubectl output and logs
- You can generate and execute diagnostic commands with AI assistance
- You resolve at least one runtime issue using Copilot's suggestions

## Key Tasks

### 01: Diagnose pod crash with Copilot

Use Copilot Chat to analyze crash logs and identify root causes.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

**Scenario:** Your backend pod is in `CrashLoopBackOff` state.

1. Get the pod crash logs:
   ```bash
   kubectl logs <backend-pod-name> -n <your-namespace> --previous
   ```

2. Copy the error output (example):
   ```
   Traceback (most recent call last):
     File "src/app.py", line 5, in <module>
       from src.config import Config
     File "src/config.py", line 23, in <module>
       DATABASE_URL = os.environ['DATABASE_URL']
   KeyError: 'DATABASE_URL'
   ```

3. Open **GitHub Copilot Chat** in VS Code (Ctrl+Shift+I or ⌘+Shift+I)

4. Paste the error and ask:
   ```
   I'm deploying a Flask app to AKS and getting this error on pod startup. 
   How do I fix it in my Kubernetes Deployment?
   
   [paste error above]
   ```

5. Copilot may suggest:
   - Add missing environment variables to the Deployment spec
   - Create a ConfigMap or Secret for database credentials
   - Use default values in config.py for optional variables

6. Apply the suggested fix (e.g., edit `deploy/k8s-template.yaml` to add env vars):
   ```yaml
   env:
   - name: DATABASE_URL
     value: "sqlite:///instance/health_platform.db"
   - name: FLASK_ENV
     value: "production"
   ```

7. Commit, push, and verify the pod starts successfully after workflow re-run

</details>

### 02: Debug ImagePullBackOff with AI assistance

Use Copilot to diagnose and fix image pull authentication failures.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

**Scenario:** Your deployment shows `ImagePullBackOff` status.

1. Get detailed pod events:
   ```bash
   kubectl describe pod <pod-name> -n <your-namespace>
   ```

2. Copy the Events section (example):
   ```
   Events:
     Type     Reason          Message
     ----     ------          -------
     Warning  Failed          Failed to pull image "ghcr.io/user/health-platform-backend:latest": 
                              failed to authorize: failed to fetch oauth token: unexpected status: 401 Unauthorized
     Warning  ImagePullBackOff  Back-off pulling image
   ```

3. Ask Copilot Chat:
   ```
   My AKS pod can't pull from GHCR and shows "401 Unauthorized". 
   I'm using an imagePullSecret called "ghcr-secret". 
   How do I troubleshoot this?
   ```

4. Copilot may suggest diagnostic commands:
   ```bash
   # Check if secret exists
   kubectl get secret ghcr-secret -n <namespace>
   
   # Verify secret content
   kubectl get secret ghcr-secret -n <namespace> -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d
   
   # Check if image exists in GHCR
   # (requires docker login first)
   ```

5. Follow up with Copilot if issues persist:
   ```
   The secret exists but still getting 401. 
   My workflow creates the secret with GHCR_READ_TOKEN. 
   What could be wrong?
   ```

6. Copilot may identify:
   - Token expired or lacks `read:packages` scope
   - Image name mismatch (check registry/owner/repo/tag)
   - Secret not correctly base64-encoded

7. Apply the fix (e.g., regenerate PAT with correct scope, update GitHub secret)

</details>

### 03: Resolve LoadBalancer timeout with Copilot

Use AI to troubleshoot frontend accessibility issues.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

**Scenario:** LoadBalancer has an EXTERNAL-IP but connection times out.

1. Gather diagnostic info:
   ```bash
   kubectl get service health-frontend -n <your-namespace>
   kubectl get pods -l app=health-frontend -n <your-namespace>
   kubectl describe service health-frontend -n <your-namespace>
   ```

2. Copy the output and ask Copilot Chat:
   ```
   My AKS LoadBalancer service has an external IP but I can't connect. 
   Here's the service description:
   
   [paste kubectl describe output]
   
   The pod shows Running but READY is 0/1. How do I debug this?
   ```

3. Copilot may suggest:
   - Check pod logs: `kubectl logs <pod-name> -n <namespace>`
   - Verify liveness/readiness probes in Deployment
   - Test connectivity from inside cluster: `kubectl run debug`
   - Check service port mapping (containerPort vs service port)

4. Follow Copilot's suggestions to check readiness probe:
   ```bash
   kubectl get deployment health-frontend -n <your-namespace> -o yaml | grep -A10 "readinessProbe"
   ```

5. If no readiness probe, ask Copilot:
   ```
   How do I add a readiness probe for a React app served by nginx on port 80?
   ```

6. Copilot provides YAML snippet:
   ```yaml
   readinessProbe:
     httpGet:
       path: /
       port: 80
     initialDelaySeconds: 5
     periodSeconds: 5
   ```

7. Add to `deploy/k8s-template.yaml`, commit, push, and verify pod becomes READY 1/1

</details>

### 04: Generate kubectl diagnostic commands with Copilot

Use Copilot to create complex troubleshooting commands on-the-fly.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. In VS Code terminal, start typing a comment describing what you need:
   ```bash
   # Get all pods in my namespace that are not running and show their restart counts
   ```

2. Press `Tab` to accept Copilot's suggestion (example):
   ```bash
   kubectl get pods -n <your-namespace> --field-selector=status.phase!=Running -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,RESTARTS:.status.containerStatuses[0].restartCount
   ```

3. Try more complex scenarios:
   ```bash
   # Find all pods using more than 100Mi memory
   ```
   
   Copilot may suggest:
   ```bash
   kubectl top pods -n <your-namespace> | awk '$3 ~ /[0-9]+Mi/ && $3+0 > 100'
   ```

4. Ask Copilot to explain commands:
   - Right-click the command in terminal
   - Select "Copilot: Explain This"
   - Read the explanation in Copilot Chat

5. Generate a diagnostic script with Copilot:
   - Create a new file: `debug-namespace.sh`
   - Type a comment:
     ```bash
     #!/bin/bash
     # Script to collect diagnostic info for an AKS namespace
     # Usage: ./debug-namespace.sh <namespace>
     ```
   - Let Copilot complete the script (example):
     ```bash
     NAMESPACE=$1
     echo "=== Pods ==="
     kubectl get pods -n $NAMESPACE
     echo "=== Services ==="
     kubectl get svc -n $NAMESPACE
     echo "=== ResourceQuota ==="
     kubectl describe resourcequota -n $NAMESPACE
     echo "=== Recent Events ==="
     kubectl get events -n $NAMESPACE --sort-by='.lastTimestamp' | tail -20
     ```

6. Run the script to quickly gather troubleshooting data

</details>

### 05: Use Copilot to fix configuration drift

Leverage AI to identify and correct Kubernetes manifest errors.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

**Scenario:** Your deployment isn't picking up changes from the latest workflow run.

1. Check current deployed image tag:
   ```bash
   kubectl get deployment health-backend -n <your-namespace> -o jsonpath='{.spec.template.spec.containers[0].image}'
   ```

2. Compare with expected tag (from workflow logs or GHCR)

3. Ask Copilot Chat:
   ```
   My GitHub workflow deploys to AKS using deploy/k8s-template.yaml. 
   The workflow substitutes $IMAGE_TAG but the deployment still uses an old tag. 
   What could cause this?
   ```

4. Copilot may identify:
   - ImagePullPolicy set to `Never` or `IfNotPresent` with same tag (e.g., `latest`)
   - Deployment not updating due to identical spec (needs restart)
   - Template substitution issue in workflow

5. Ask for a solution:
   ```
   How do I force Kubernetes to always pull the latest image, 
   even if the tag name hasn't changed?
   ```

6. Copilot suggests:
   - Use unique tags (commit SHA instead of `latest`)
   - Set `imagePullPolicy: Always`
   - Add a rollout restart: `kubectl rollout restart deployment/<name> -n <namespace>`

7. Implement the fix in `deploy/k8s-template.yaml`:
   ```yaml
   image: ghcr.io/${{ github.repository_owner }}/health-platform-backend:${{ github.sha }}
   imagePullPolicy: Always
   ```

8. Commit, push, and verify the deployment updates with the new SHA-tagged image

</details>

### 06: Interactive troubleshooting session with Copilot

Conduct a multi-turn conversation to resolve a complex issue.

<details markdown="block">
<summary><strong>Expand this section for detailed steps</strong></summary>

1. Open Copilot Chat and start with a high-level problem description:
   ```
   I deployed my Flask/React app to AKS via GitHub Actions. 
   The frontend LoadBalancer works but shows "Network Error" when calling the backend. 
   Both pods are running. What should I check?
   ```

2. Copilot suggests initial checks (e.g., service exists, CORS, network policy)

3. Execute suggested commands and paste results back:
   ```
   Here's the backend service:
   [paste kubectl describe service health-backend output]
   
   And frontend logs show:
   [paste relevant log lines]
   ```

4. Copilot analyzes and may ask clarifying questions:
   - "What's the backend URL configured in your frontend?"
   - "Are you using ClusterIP or LoadBalancer for the backend?"

5. Continue the conversation:
   ```
   The frontend env var REACT_APP_API_URL is set to 
   http://health-backend:5000 but that's the internal service name. 
   How do I fix this?
   ```

6. Copilot explains:
   - Frontend running in browser can't resolve cluster-internal DNS
   - Need to use backend LoadBalancer external IP or relative path (`/api`)
   - Or configure backend as ClusterIP and route through frontend's nginx

7. Ask for implementation steps:
   ```
   Show me how to configure nginx in the frontend to proxy /api to 
   the backend service health-backend:5000
   ```

8. Copilot provides nginx.conf snippet and Dockerfile changes

9. Implement, commit, push, and verify the fix works

</details>
