# Requirement: 健康管理入口重构与检查报告统一管理

> 状态：Draft
> GitHub Issue: #33 https://github.com/workshop-copilot/health_platform/issues/33
> 说明：本需求用于统一承载健康记录、既往病史、检查报告三类健康资料，并重构左侧菜单入口。
> 用户确认口径：菜单统一使用“检查报告”；附件支持图片、Excel、PDF；检查报告必须绑定家庭成员。

## 1. Background & Value
- **User Story**：作为家庭健康平台用户，我希望在同一个健康管理入口下统一维护健康记录、既往病史和医院检查报告，这样我可以完整保存家庭成员的健康资料，并在复诊、回顾和家庭健康管理时快速找到历史信息。
- **Business Value**：
  - 统一健康资料入口，降低用户在多个页面之间切换的认知成本。
  - 将检查报告从既往病史中独立出来，便于按成员、时间、医院、类型和关键词查找。
  - 支持用户沉淀医院检查资料，提升平台从“日常记录工具”到“家庭健康档案”的价值。
  - 为后续报告分析、趋势分析、病史关联分析打下基础。

## 2. Scope & Boundaries

### In-Scope
- 左侧菜单新增或调整为“健康管理”一级入口。
- “健康管理”下提供三个二级菜单：
  - 健康记录
  - 既往病史
  - 检查报告
- “检查报告”作为独立资料类型，不作为既往病史的内部字段。
- 用户可以为自己或有权限访问的家庭成员上传检查报告。
- 每份检查报告必须绑定一个家庭成员。
- 检查报告附件支持图片、Excel、PDF。
- 用户可以查看已上传报告列表，并识别每份报告的上传时间和主要信息。
- 用户可以查看或下载已上传报告附件。
- 支持按成员查看检查报告。
- 支持按时间、医院/机构、报告类型等维度筛选或检索检查报告。

### Out-of-Scope
- AI 自动诊断或智能结论生成。
- OCR 全自动识别并结构化所有报告内容。
- 复杂医学影像阅片器。
- 医院、科室、报告类型的标准化字典治理。
- 报告附件的多人协作审批流。
- 与医院系统直接对接拉取报告。

## 3. Product Structure

### 3.1 Navigation
- 一级菜单：**健康管理**
- 二级菜单：
  - **健康记录**：管理血压、心率等日常健康数据。
  - **既往病史**：管理疾病名称、疾病状态、发现/确诊时间、是否仍存在、是否仍在服药等信息。
  - **检查报告**：管理医院检查报告和相关附件。

### 3.2 Report List Experience
检查报告列表应帮助用户快速回答：
- 我给哪个家庭成员上传过报告？
- 报告是什么类型或名称？
- 报告是什么时候检查或出具的？
- 我是什么时候上传的？
- 报告来自哪家医院或机构？
- 是否可以打开、查看或下载原始附件？

### 3.3 Report Creation Experience
用户新增检查报告时，应先选择或明确报告归属的家庭成员，再填写报告基础信息并上传附件。页面文案统一使用“检查报告”，避免同一能力在导航中叫“报告管理”、在页面中叫“检查报告”造成理解成本。

## 4. Report Information Requirements
每份检查报告建议包含以下用户可理解的信息：
- 所属家庭成员
- 报告名称
- 报告类型
- 检查/报告时间
- 上传时间
- 医院或机构
- 科室（可选）
- 检查结论或摘要（可选）
- 异常项摘要（可选）
- 备注（可选）
- 附件，支持图片、Excel、PDF
- 关联既往病史（后续可选能力）

## 5. Business Rules
- 所有检查报告必须明确绑定一个家庭成员。
- 用户只能为自己或有权限访问的家庭成员上传和查看检查报告。
- 检查报告必须作为独立记录管理，不依附于既往病史。
- 检查报告可以在后续关联一个或多个既往病史，但创建时不要求强制绑定病史。
- 附件类型本期支持图片、Excel、PDF。
- 列表中必须展示上传时间，方便用户回顾“什么时候上传了哪些信息”。
- 健康记录、既往病史、检查报告三类资料的成员选择逻辑保持一致。

## 6. Acceptance Criteria (AC)
- [ ] AC1：左侧菜单中存在“健康管理”一级入口。
- [ ] AC2：“健康管理”下可看到“健康记录 / 既往病史 / 检查报告”三个二级菜单。
- [ ] AC3：菜单和页面命名统一使用“检查报告”。
- [ ] AC4：用户可以进入“检查报告”页面查看报告列表。
- [ ] AC5：用户可以新增检查报告，并且新增时必须选择家庭成员。
- [ ] AC6：用户可以上传图片格式的检查报告附件。
- [ ] AC7：用户可以上传 Excel 格式的检查报告附件。
- [ ] AC8：用户可以上传 PDF 格式的检查报告附件。
- [ ] AC9：检查报告列表展示报告名称、所属家庭成员、报告类型、检查/报告时间、上传时间、医院/机构。
- [ ] AC10：用户可以查看或下载已上传的检查报告附件。
- [ ] AC11：用户可以按家庭成员查看检查报告。
- [ ] AC12：用户可以按时间范围、医院/机构、报告类型筛选检查报告。
- [ ] AC13：检查报告作为独立记录类型保存，不依附于既往病史。
- [ ] AC14：健康记录、既往病史、检查报告在成员选择逻辑上保持一致。
- [ ] AC15：后续可扩展检查报告与既往病史的关联能力。

## 7. Non-Functional Requirements
- **Usability**：入口命名直观一致，避免“报告管理”和“检查报告”混用。
- **Security & Privacy**：检查报告属于敏感健康资料，只允许授权用户访问对应家庭成员的报告。
- **Extensibility**：后续可扩展附件预览、标签、统计、分析、病史关联能力。
- **Searchability**：报告需保留足够基础信息，便于筛选和回顾。
- **Internationalization**：中英文文案预留扩展空间。

## 8. Suggested Delivery Phases
- 第一阶段：完成“健康管理”菜单重构与三个二级入口拆分。
- 第二阶段：上线“检查报告”基础录入、附件上传和列表查看能力。
- 第三阶段：支持报告筛选、检索、查看和下载体验优化。
- 第四阶段：支持检查报告与既往病史的关联分析。
