# Requirement: E2E 回归测试（注册/登录/健康记录/成员/修改，中文优先）

## 1. Background & Value
- **User Story**: 作为测试/发布负责人，我希望可以手动触发一条稳定的 UI 端到端回归流程，以便在发布前快速验证核心业务链路未被破坏。
- **Business Value**:
  - 降低发布风险：快速发现注册/登录/数据录入/修改等关键路径回归问题。
  - 提升可追溯性：通过时间戳命名避免数据冲突，便于定位每次回归的测试数据。
  - 兼顾国际化：优先保障中文 UI 的可用性与稳定性。

## 2. Scope & Boundaries
- **In-Scope**:
  - UI 端到端（E2E）回归测试：从新用户注册开始，覆盖登录、语言设置、健康记录创建、家庭成员创建、成员健康记录创建、健康记录修改。
  - 语言覆盖：默认以中文 UI 跑通全流程；登录后检查用户设置中的当前语言，若非中文则切换为中文后继续。
  - 数据唯一性：新用户用户名与 email 必须包含“分钟级时间戳”；新建家庭成员名称也包含时间戳。
  - 校验重点：血压字段覆盖“合法输入可提交”、“非法越界输入不可提交/有错误状态”、“修改后生效”。
  - 触发方式：支持手动触发执行（用于回归验证）。
- **Out-of-Scope**（本阶段）:
  - 英文 UI 完整跑同一套全流程（后续迭代补充）。
  - 对具体错误提示文案（中文/英文）进行严格断言（先保证流程可稳定跑通）。
  - 覆盖所有健康字段/所有边界条件的穷尽测试（本需求聚焦关键回归链路）。

## 3. Acceptance Criteria (AC)
- [ ] AC1: 回归测试可以被手动触发运行，并输出清晰的通过/失败结果。
- [ ] AC2: 新用户注册数据满足唯一性：
  - 用户名包含分钟级时间戳，格式建议：`YYYYMMDD-HHmm-demo`（示例：`20260113-0932-demo`）。
  - email 同步包含同样的分钟级时间戳信息，避免重复运行冲突。
- [ ] AC3: 新用户注册后可以成功登录。
- [ ] AC4: 登录后进入用户设置检查当前语言：若为英文，则切换为中文；并能在 UI 上确认已处于中文状态（例如出现中文文案/语言显示为中文）。
- [ ] AC5: 能为默认成员（自己）创建 1 条合法血压的健康记录并保存成功。
- [ ] AC6: 尝试输入越界血压时，页面出现错误状态且无法提交（本阶段不强依赖具体错误文案）。
- [ ] AC7: 能创建 1 个家庭成员（成员名包含时间戳），并为该成员创建“同一天”的 1 条健康记录。
- [ ] AC8: 能修改既有健康记录的血压字段；保存后在界面上可确认修改已生效。

## 4. Non-Functional Requirements
- **Stability**: 可在同一天多次运行而不发生数据命名冲突。
- **i18n**: 优先保障中文 UI 的稳定可执行；英文 UI 在后续迭代补齐。
- **Maintainability**: 流程步骤与断言尽量稳定，避免对易变化的文案/样式产生强耦合。
