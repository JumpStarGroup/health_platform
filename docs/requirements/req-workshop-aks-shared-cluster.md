
# 需求文档：Workshop 简化——共享 AKS 集群 + 分支=Namespace 自动部署（GHCR + LoadBalancer + Namespace 配额）

- **Owner**: Product Management
- **Status**: Draft
- **Date**: 2026-01-07

## 1. 背景 & 价值

### 1.1 为什么从 App Service 迁移到 AKS
Workshop 的目标不是“把应用跑起来”，而是让学员体验一条完整的工程闭环：本地开发、测试、CI/CD、容器化与部署、可访问验证、产出交付物。相较 App Service，AKS 更贴近真实团队在容器平台上的交付方式，且具备以下价值：

- **更一致的交付路径**：同一套 Docker 镜像与部署范式可覆盖开发/测试/演示环境，减少平台差异导致的教学摩擦。
- **更契合 DevOps 教学**：围绕镜像、工作负载、命名空间隔离、资源配额等概念进行实践，比 App Service 更可迁移到生产团队。
- **更可控的环境标准化**：将部署过程固化到 GitHub Actions（而非手工点选/配置），降低“学员环境不一致”带来的排障成本。

### 1.2 为什么使用“共享 AKS 集群”
为每位学员单独创建集群成本高、运维复杂、且不利于统一管理；共享集群配合 Namespace 级隔离可以兼顾规模化与可控：

- **成本意识**：共享集群降低单位学员的资源与运维成本。
- **教学稳定性**：管理员统一维护集群与对外访问入口，学员只关注代码与需求本身。
- **更贴近真实多人协作**：同一集群多环境并行，强调隔离、可追溯与并发安全。

### 1.3 为什么学员只需要 GitHub（不要求 Azure Portal/订阅）
Workshop 希望学员将注意力集中在“需求—实现—验证—交付”而非云平台操作：

- **降低门槛**：学员无需 Azure 订阅、无需额外账号权限申请。
- **可重复与可追溯**：每次部署均由提交触发，行为在 GitHub 上可审计、可回放。
- **安全与合规**：将敏感配置集中由管理员预置，学员无需接触密钥/凭据。

## 2. 目标（Outcomes）

- 学员以“分支”为单位创建独立环境：`branch -> namespace`。
- 学员仅通过 GitHub（提交/PR/Actions）触发从构建到部署的全流程。
- 部署完成后可获得可访问的前端地址（LoadBalancer），用于验证与演示。
- 共享集群具备最基本的资源公平机制（Namespace 配额与默认限制）。

## 3. 范围（Scope）

### 3.1 范围内

**部署与隔离**
- 分支与命名空间一一映射：同一分支重复部署落到同一 Namespace；不同分支互不覆盖。
- 首次部署可自动准备该分支对应的 Namespace（创建或初始化）。
- 同一 Namespace 内部署前端与后端（满足 Workshop 演示闭环）。

**镜像与仓库**
- 镜像仓库使用 GHCR。
- 集群侧具备拉取 GHCR 私有镜像的能力（由管理员预置凭据与访问方式）。

**对外访问**
- 前端通过 LoadBalancer 暴露对外访问入口。
- Workflow 产出“可复制”的访问地址，作为验收输出之一。

**资源约束**
- 每个学员 Namespace 默认启用资源配额（ResourceQuota）与默认资源限制（LimitRange），避免资源无限制占用。

### 3.2 不包含（Out of Scope）

- 不要求引入 Ingress/域名/HTTPS（可作为后续增强，但不作为本需求验收条件）。
- 不要求实现更强的集群策略治理（例如 NetworkPolicy、PodSecurity、OPA/Gatekeeper 等）。
- 不要求自动回收/清理学员 Namespace（可由管理员在 Workshop 后统一处理）。
- 不做生产级容量规划、成本报表、告警系统或 SLO 承诺。
- 不涉及任何“阈值治理 / health threshold”相关内容。

## 4. 关键用户故事（User Stories）

1) 作为学员，我可以在本地跑起来前后端，确认基础开发环境无误。
2) 作为学员，我可以在 Copilot 协助下完成指定需求并通过测试验证。
3) 作为学员，我只需推送代码到 GitHub，就能自动部署到 AKS，并拿到可访问的前端链接。
4) 作为学员，我可以在代码与部署完成后，产出系统功能说明与 PPT 需求书，形成完整交付物。

## 5. 验收标准（Acceptance Criteria）

### 5.1 实验场景覆盖（必须覆盖四个场景）

**场景 A：本地运行**
- A1：按开发指南启动后端与前端，本地可访问前端页面且页面能正常加载。
- A2：本地运行不要求任何 Azure/AKS 权限或凭据。

**场景 B：Copilot 完成 `req-health-record-validation-update`**
- B1：学员在 Copilot 协助下完成 [docs/requirements/req-health-record-validation-update.md](docs/requirements/req-health-record-validation-update.md) 的实现。
- B2：对应自动化测试可通过（以仓库现有 Pytest 为准），失败时输出错误信息足以定位是校验逻辑问题还是测试环境问题。

**场景 C：提交触发自动部署且可访问前端**
- C1：推送到某个分支后，GitHub Actions 自动执行构建与部署。
- C2：部署目标 Namespace 可由分支名稳定推导；同一分支多次部署不创建“重复环境”。
- C3：部署完成后，Actions 输出可复制的前端访问地址；用浏览器访问页面可正常加载（非 4xx/5xx）。
- C4：至少验证两个不同分支并行部署时互不覆盖：一个分支的部署不影响另一个分支的前端访问。

**场景 D：生成系统功能说明与 PPT 需求书**
- D1：仓库内产出一份“系统功能说明文档”（内容聚焦功能与使用方式，不要求设计稿）。
- D2：产出一份“PPT 功能需求书”（可用 Markdown/PowerPoint/其他可打开格式，具体格式由 Workshop 指定）。
- D3：交付物中明确说明：本次 Workshop 的部署模式为“共享 AKS + 分支=Namespace”，并包含至少一个可访问的演示链接或截图。

### 5.2 平台能力验收（通用）

- P1（可追溯）：每次部署在 Actions 日志中明确展示：分支名、目标 Namespace、镜像标识（tag 或 digest）、触发的提交 SHA。
- P2（安全）：任何敏感信息（令牌、密钥等）不得出现在 Actions 日志与构建产物中。
- P3（配额生效）：Namespace 内可观测到 ResourceQuota 与 LimitRange；当资源请求超出限制时，部署应以可理解的方式失败并给出原因提示（例如“超过配额/默认限制”）。

## 6. 非功能需求（NFR）

### 6.1 安全
- 机密信息仅通过 GitHub 的安全机制进行注入与管理（例如 Secrets/Environments），不得硬编码。
- CI/CD 使用最小权限原则：只授予完成部署所需的最小范围。

### 6.2 隔离
- 分支间隔离以 Namespace 为边界：不同分支资源、工作负载与对外入口互不覆盖。
- 默认启用 Namespace 资源配额与默认限制，防止共享集群被单一分支耗尽。

### 6.3 可追溯
- 能从 GitHub Actions 追溯到“谁在何时以哪个提交部署到哪个 Namespace”，并能定位对应镜像版本。

### 6.4 成本意识
- 设计应优先复用共享能力（共享集群、统一镜像仓库、统一对外入口规划）。
- 不追求“为学员每人一套长期环境”，以可回收、可并发、可复用为导向。

### 6.5 国际化
- 不强制要求国际化（i18n）；文档与 UI 以 Workshop 需要为主。

## 7. 管理员前置（仅列出需要预先准备的事项）

> 本节只描述“需要准备什么”，不包含实现细节/命令/YAML。

- 一套可用的 AKS 集群（Workshop 共享），并明确集群的负责人/值班联系人。
- 一组可用于 Workshop 的对外访问入口能力：支持为前端提供 LoadBalancer 访问（含必要的公网资源与配额）。
- 集群侧已具备从 GHCR 拉取私有镜像的能力（长期有效的读取凭据或等效机制），并完成仓库/组织权限配置。
- GitHub 仓库中已配置用于部署的必要 Secrets/Environments（例如集群访问凭据、必要的环境变量），并确认对学员不可见。
- 已定义 Namespace 命名规则（从分支名派生的可用字符集/长度/冲突处理原则），并对学员可见。
- 已定义每个 Namespace 的资源约束策略（ResourceQuota + LimitRange 的目标形态），并确认不会影响 Workshop 基本运行。
- 已定义基础审计与回溯方式（至少：Actions 运行记录保留策略、管理员如何在需要时查看部署状态）。

## 8. 风险与对策（简述）

- 镜像拉取失败（权限/凭据）：要求管理员在开课前完成一次“空跑部署”验证 GHCR 拉取链路。
- LoadBalancer 资源不足：提前规划并限制学员并发规模，必要时安排分批次实验。
- 分支名不符合 Namespace 规则：要求清晰的命名规则与失败提示，避免学员卡住。
